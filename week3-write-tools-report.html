03预校验：三类校验，失败即终止

复用业务 DTO做参数校验，因此 AI 请求和 REST 请求报的是同一套错误。

校验层规则来源实测拦截样例
参数合法性 CreateUserDto / UpdateFlightRecordDto（class-validator） 非法邮箱、密码少于 8 位、月份 13、非法角色
权限校验 身份透传 + adminOnly 普通用户调用写入工具 → 403 仅管理员可用
业务规则 业务 Service 自身校验方法 邮箱重复、目标不存在、删除自己、最后一位管理员
错误信息带字段级明细（meta.details: ["email: 邮箱格式不正确","password: 密码至少 8 位"]）， 与 ValidationPipe 返回格式一致，前端可直接展示。

04需求偏差（如实说明）

任务写的 7 个写入工具已全部落地，但有两个前提在代码里原本不存在，我补齐了。

任务原文代码现状处理方式

"注入现有 AirlineService"（航班 3 类写操作） FlightDelayService 原本只有 5 个只读方法 补齐 createRecord / updateRecord / removeRecord / findRecordById + 粒度唯一性（年-月-航司-机场）与字段范围校验

补齐的写方法都放在业务 Service里，写入工具一行 SQL 都没有——合规走查脚本会持续守住这一点。

06过程中修掉的 4 个真实缺陷

缺陷影响修复
preview() 端点绕过了预校验 非法邮箱/重复邮箱也能生成预览，用户会去确认一个注定失败的操作 预览前强制执行同一套三层校验
业务接口不返回记录 id 无法定位要改/删的那条航班记录，写入工具实际不可用 findAll 增加 id 列（bigint 转 Number）
357 条审计 duration_ms 为 NULL 性能分位数统计失真 审计写入默认 0，并回填历史数据
「新建一个用户」被只读工具抢走 聊天里永远触发不到写入工具（强关键词 用户 属于 user.query） 写意图动词加权 + 实体词区分用户/航班记录；并允许模型选择写入工具（执行仍需令牌）
