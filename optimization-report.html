一、做了什么

优化项实现方式
1. 工具参数 Schema 新增 tools/tool-schema.ts（共享片段 flightFilters() / schema()），5 个工具的 ToolDefinition 补上 parameters（OpenAI function-calling 形状）。关键词与 Schema 同源，两者不会漂移。
2. 适配器支持 Function Calling LlmCompletionRequest 增加 tools / toolChoice；响应解析 tool_calls。兼容兜底：服务端拒绝 tools 字段（400/404/422 且错误信息含 tool/function）时自动重试不带 tools，并标记 toolsUnsupported 交给关键词路由。
3. 分层提示词 原 4 行 SYSTEM_PROMPT 拆为五层：身份 / 数据边界（2009-01–2018-12 美国航班）/ 工具使用规范 / 输出格式 / 安全边界（禁止编造数字、禁止声称执行写操作、不确定就反问）。
4. 混合路由（核心） AI_TOOL_ROUTING=auto：强关键词快捷（仅按 strongKeywords，命中即执行）→ 含多步信号则跳过 → 模型 function calling（最多 3 轮 × 4 工具，结果回喂）→ 关键词兜底 → 纯聊天。
关键规则：模型可达且决定不调工具时，该判断优先，关键词不得覆盖。
5. 多步编排 模型 ↔ 工具循环最多 3 轮；轮次耗尽后强制一次纯文本总结兜底，且始终保留首个成功工具的 payload，真实数据绝不丢弃。

关于响应速度的诚实说明：隐式问法的绝对延迟确实上升了（多一次模型往返）。这是拿延迟换正确性的权衡——原方案 36 ms 但答错。 为把代价压到最小，混合路由让 43% 的请求（明确问法）保持零模型调用；相比"全部交给模型"的方案， 平均耗时从 2790 ms 降到 1669 ms（−40%）、token 从 41243 降到 23865（−42%），同时准确率反而更高。

三、过程中修掉的真实缺陷

  • 纯模型路由会让明确问法退化（100%→80%，"航司层级气泡图"被漏掉）→ 加入强关键词快捷路径。
  • 模型常省略可选参数：未传 dimension，把"哪家航司取消最多"折叠成 1 个分组 → mergeParams() 模型参数优先、规则抽取补齐。
  • 强关键词抢走多步问题："分别给我 2017 和 2018"被折叠成单年 → 多步信号检测（分别/对比/两年/趋势…）跳过快捷路径。
  • 模型陷入重复调用循环 → 轮次上限 + 强制总结兜底。
  • 原实现最危险的行为："帮我订一张机票"命中 flight.query，返回"共 150,860 条航班记录"，看起来像成功。

五、未做（诚实标注）

  • 未落地 RAG：pgvector 已就绪，但无 embedding 服务与文档源；且当前仅 5 个工具，不需要 Tool RAG。建议先补"指标口径问答"知识库。
  • 等价实现 LangGraph：@langchain/langgraph 已装但 @langchain/core peer 缺失。多步能力用自写循环实现；langgraph-checkpointer.ts 已是 LangGraph 契约实现，将来接入可直接复用。
  • 已知限制 复杂多步对比（如"分别给我 2017 和 2018 并比较"）仍受限于模型理解与工具字段覆盖，未达完美。
